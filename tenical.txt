NEXUS Scheduler — Technical Architecture Document

1. What is NEXUS?
NEXUS is a custom Kubernetes scheduler written in Go. It acts as a secondary scheduler that runs alongside the default Kubernetes scheduler inside the same cluster. It does not replace the default scheduler — it augments it.
The core idea:
During normal traffic, let the default scheduler do its job.
During a traffic spike, NEXUS takes over scheduling for specific "latency-critical" pods and places them intelligently based on service dependencies (e.g., Cart near Payment).

3. How Does NEXUS Integrate with Kubernetes?
3.1 Dual-Scheduler Architecture
Kubernetes supports running multiple schedulers simultaneously. Each pod declares which scheduler should handle it via the schedulerName field in its spec.
How it works:
Pods with schedulerName: default-scheduler
→ Handled by Kubernetes default scheduler (normal behavior)
Pods with schedulerName: nexus-scheduler
→ Handled by NEXUS
When we deploy NEXUS, we patch the Online Boutique deployments to set:
schedulerName: nexus-scheduler

on latency-critical services:
CartService
PaymentService
CheckoutService
Non-critical services (AdService, EmailService, RecommendationService, etc.) remain on the default scheduler.

3.2 How NEXUS Runs in the Cluster
NEXUS runs as a regular Kubernetes Deployment (a single Pod).
It has:
A ServiceAccount with RBAC permissions to:
Read Pods
Read Nodes
Read Events
Create Bindings (assign a pod to a node)
A Service exposing port 9099 for Prometheus to scrape metrics
A ServiceMonitor so Prometheus automatically discovers it
It is deployed into its own namespace:
nexus-system


4. How Event-Driven Triggering Works
This is the most critical part.
NEXUS does NOT poll the API server in a tight loop. It uses Kubernetes Informers, which are event-driven watchers.

4.1 What is a Kubernetes Informer?
An Informer is a Go library that establishes a long-lived watch connection to the Kubernetes API server.
Instead of repeatedly asking:
"Are there new pods?"
the API server pushes events to NEXUS the moment something changes.
Three types of events:
AddFunc — A new pod appears
UpdateFunc — An existing pod's status changes
DeleteFunc — A pod is removed

4.2 The Triggering Flow (Step by Step)
Step 1: Pod Appears as "Pending"
When a traffic spike hits and Kubernetes creates new pods (via HPA auto-scaling or crash recovery), those pods start in Pending state with no node assigned.
The Informer’s AddFunc fires. NEXUS checks:
Is the pod's schedulerName set to "nexus-scheduler"?
Is nodeName empty?
Is the pod phase Pending?
If all three are true → NEXUS adds it to its internal pendingPods queue.

Step 2: Spike Detection (IDLE → ACTIVE Transition)
Every time a pod is added to the pending queue, NEXUS checks:
"Is this a spike?"
Current logic (basic):
If pendingPods count ≥ spikeThreshold (5) → Switch to ACTIVE state.
Upgraded logic (mentor’s Algorithm 1):
NEXUS queries Prometheus for:
QPS > QPS_threshold
ErrorRate > Error_threshold
HPA scale-up events detected
If ANY condition is true → SPIKE_EVENT = TRUE → Switch to ACTIVE state.

Step 3: Scheduling Decision (ACTIVE State)
This follows mentor’s Algorithm 4.
Check 1: Is SPIKE_EVENT == FALSE?
YES → Use default scheduler logic (pick first available node).
This is dormant behavior.

Check 2: Is the pod part of a Coordination Group?
NO → Use default scheduler logic
YES → Proceed to smart placement

Check 3: Smart Placement (Filter → Score → Bind)
Filter
Get all nodes
Remove nodes that are:
CPU/Memory exhausted
Tainted against this pod
Result: EligibleNodes
Score
For each eligible node:
Calculate locality score
Higher score if node already runs pods from same Coordination Group
Example:
Node A has PaymentService → Score = 100 (for CartService)
Node B has no related service → Score = 0
Node C has CheckoutService → Score = 50
Bind
Pick node with highest score
Create Kubernetes Binding object
Pod is assigned to that node

Step 4: Cooldown (ACTIVE → IDLE)
Background goroutine (every 5 seconds):
Is state ACTIVE?
Is pendingPods empty?
Has 30 seconds passed since last spike?
If all true → Switch back to IDLE.

5.3 scorer.go — New File
Implements Node Scoring Engine.
Contains:
NodeScorer struct
Score(pod, eligibleNodes, coordinationGroup)
Logic:
For each node → list running pods
Check if running pods belong to same Coordination Group
Count group members
Highest count = highest score
Tie-breaker → more available CPU/Memory
FilterNodes(nodes) removes:
Unschedulable nodes
Tainted nodes
Resource-insufficient nodes
Scoring Formula:
NodeScore = (GroupPodsOnNode × 100)
          + (AvailableCPU × 10)
          + (AvailableMemory × 1)

Locality is primary factor. Resources are secondary.

5.4 spike.go — New File
Implements Spike Detection Module.
Contains:
SpikeDetector struct
Detect() function
Prometheus metrics queried:
QPS

Error Rate
sum(rate(http_server_request_count{response_code=~"5.."}[1m]))

Environment variables:

SPIKE_ERROR_THRESHOLD (default: 50)
Fallback:
If Prometheus unreachable → use pending pod count method.

6. Complete Lifecycle: Normal → Spike → Recovery → Normal

Phase 1: Normal Traffic (IDLE)
NEXUS running
CPU near zero
Informer watching
Default scheduler handles routine scheduling
State: IDLE
Prometheus metric:
nexus_scheduler_state = 0



Phase 2: Spike Hits (Activation)
Traffic surge
HPA scales
Pods Pending
AddFunc events
Added to pending queue
Prometheus shows QPS spike
State change: IDLE → ACTIVE
Metric:
nexus_scheduler_state = 1



Phase 3: Smart Scheduling
Check dependency group
Score nodes
CartService sees PaymentService on Node 2
Node 2 highest score
Bind CartService to Node 2
Result: Local communication (nanoseconds vs milliseconds)

Phase 4: Cooldown
Pending empty
Traffic normal
30s cooldown
ACTIVE → IDLE
CPU drops
