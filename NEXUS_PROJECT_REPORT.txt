2. RESEARCH ARCHITECTURE
================================================================================

How NEXUS Integrates with Kubernetes:

    +---------------------------------------------------+
    |               kube-scheduler                      |
    |      (calls NEXUS at /filter & /prioritize)       |
    +-------------------------+-------------------------+
                              |
                    +---------v---------+
                    |  NEXUS Extender   |
                    |    (main.go)      |
                    +---+-----+-----+--+
                        |     |     |
              +---------+     |     +---------+
              v               v               v
        +-----------+   +-----------+   +-----------+
        |   Spike   |   |   Gang    |   |   Node    |
        | Detector  |   | Manager   |   |  Scorer   |
        | (spike.go)|   | (gang.go) |   |(scorer.go)|
        +-----+-----+   +-----+-----+   +-----------+
              |               |
              v               v
        +-----------+   +-----------+
        | Prometheus|   |Dependency |
        |   Query   |   |   Graph   |
        +-----------+   +-----------+


Event-Driven State Machine:

    IDLE -----(spike detected)-----> ACTIVE
     ^                                  |
     |                                  |-- Build DAG
     |                                  |-- Form Gang
     +---(cooldown + dissolve gang)-----+-- Score Nodes
                                        +-- Advise kube-scheduler

Key Design Decisions:
  * Zero Overhead in Steady State: When IDLE, NEXUS returns "no opinion"
    to kube-scheduler, adding zero latency to the scheduling pipeline.
  * Ephemeral Gangs: Gangs are created only during spikes and dissolved
    after cooldown. No persistent state is maintained.
  * Extender Pattern: NEXUS does not replace kube-scheduler; it advises it.
    This ensures safety and full compatibility with vanilla Kubernetes.

3. RESOURCE CONSTRAINT — BLOCKING ISSUE
================================================================================

THE PROBLEM:
The local development environment (Docker Desktop on Windows) has a hard
ceiling of approximately 3.8 GB RAM. The following components compete for
this limited memory:

    Component                                          Memory Usage
    --------------------------------------------------+-----------
    Kubernetes System Pods                             |  ~800 MB
    (API Server, etcd, CoreDNS, Scheduler, etc.)      |
    --------------------------------------------------+-----------
    Online Boutique Microservices (11 services)        | ~1200 MB
    --------------------------------------------------+-----------
    NEXUS Scheduler Extender                           |  ~128 MB
    --------------------------------------------------+-----------
    Prometheus                                         |  ~256 MB
    --------------------------------------------------+-----------
    Grafana                                            |  ~256 MB
    --------------------------------------------------+-----------
    Locust                                             |  ~256 MB
    --------------------------------------------------+-----------
    TOTAL REQUIRED                                     | ~2900 MB
    --------------------------------------------------+-----------
    AVAILABLE (Docker Desktop Limit)                   | ~3072 MB
    --------------------------------------------------+-----------

OBSERVED SYMPTOMS:

  1) Node Flapping: The Minikube node oscillates between "Ready" and
     "NotReady" states due to memory pressure, causing all pods to restart
     repeatedly.

  2) DNS Failures: CoreDNS crashes under memory pressure, returning
     "server misbehaving" errors and breaking inter-service communication.
     This is the root cause of the "500 Internal Server Error" seen on
     the frontend.

  3) Pod CrashLoopBackOff: Services fail health probes during resource
     contention, enter CrashLoopBackOff, and are repeatedly killed and
     restarted by Kubernetes.

  4) Prometheus Stuck: The Prometheus container cannot fully initialize
     because pulling the image and starting the time-series database
     requires more memory than is available when other services are running.


IMPACT ON VALIDATION:

  [DONE]    Code is complete and correct — all modules compile and run
  [DONE]    Deployment manifests are correct — all resources created successfully
  [DONE]    Monitoring stack manifests are ready — Prometheus, Grafana, Locust
  [BLOCKED] Full-scale load testing — running all components simultaneously
            exceeds available RAM
  [BLOCKED] Grafana dashboards show no data — Prometheus cannot fully start
            alongside the application


RECOMMENDED RESOLUTION:

  Option 1: Increase Docker Desktop memory to 6 GB
             (Simplest fix; allows all components to run simultaneously)

  Option 2: Use a cloud VM (e.g., GCP e2-medium, AWS t3.medium)
             (Free tier available; mirrors production environment)

  Option 3: Run monitoring stack on the host machine separately
             (Keep Boutique on Minikube, monitoring tools on localhost)
